# mcptree v0.2 — Design Spec

**Date:** 2026-07-28
**Status:** Approved (design phase)
**Predecessor:** `2026-07-23-mcptree-design.md` (v0.1, shipped)
**Origin:** full-code review of v0.1 (this session). Four verified defects, three
ideological gaps. This spec fixes all of them.

---

## 1. Motivation

The v0.1 review found the engineering strong but flagged:

**Verified defects**

1. The nested-boolean-key guard in `loader.py` only trips on multi-key mixed-type
   mappings (it relies on `json.dumps(sort_keys=True)` comparisons). A single-key
   `args: { on: x }` loads silently as `{True: 'x'}`. Integer keys (`200:`) slip
   through the same way.
2. `validate.py` follows an `ask` node's `next` for reachability even when
   `options` is present — but the runtime ignores that edge, so a node reachable
   only through it passes validation yet is unreachable.
3. `JsonSessionStore._path` sanitizes ids by dropping characters, so distinct ids
   collide (`"ses_a.b/c"` → `ses_abc.json`) and a malformed id can load someone
   else's session instead of raising.
4. `tree_answer` is load→submit→save with no in-process lock; two concurrent
   calls for one session can both pass the step check (last-write-wins).

**Ideological gaps**

- The docs imply determinism/auditability stronger than the honor-system trust
  model can deliver (all inputs are agent-reported).
- `ask` — the *human's* node — never actually reaches the human; the agent can
  answer it and the trace cannot tell.
- No data flow: action `args` are frozen at authoring time, predicates are
  single-op, judgment results vanish into routing. Real runbooks are
  parameterized by what they learn.

## 2. Decisions (user-approved)

- **Spec bumps to 0.2, gated.** The engine accepts documents declaring `"0.1"`
  or `"0.2"`. New tree-format features used in a `"0.1"` document fail parsing
  with a "requires mcptree 0.2" error. `trees/incident.yaml` stays a 0.1
  document (back-compat proof; keeps all existing docs/screenshots valid).
- **Elicitation on by default, graceful fallback.** Opt-out via
  `DecisionTrees(..., elicit=False)`.
- **Sub-tree composition is deferred** to a later version. Also out of scope:
  PyPI publishing, session GC/listing (product follow-ups, not ideology).

## 3. Phase 1 — defect fixes (no tree-format change)

### 3.1 Loader: reject non-string mapping keys everywhere

After the existing node-level `on:` normalization, recursively walk the parsed
document. Any remaining mapping key that is not a `str` fails loading:

```
TreeLoadError: <path>: non-string mapping key True at nodes.a.args — quote
YAML boolean-like keys ('on', 'yes', ...) and other non-string scalars
```

This subsumes booleans and integers. The canonical `json.dumps(sort_keys=True)`
check stays (it still catches non-JSON *values* like dates).

### 3.2 Validator: `ask` with both `options` and `next` is invalid

New validation issue: `ask node with 'options' must not also have 'next' (it is
ignored at runtime)`. Reachability (`_refs` for the traversal) no longer follows
`next` when `options` is present, so nodes reachable only through the dead edge
are correctly flagged unreachable. Strictly stricter: any tree newly rejected
was latently broken. Applies to all spec versions the engine loads (documented
as a 0.2 tightening in SPEC.md §2.8).

### 3.3 Sessions: strict id validation

`JsonSessionStore` accepts only ids matching `^ses_[0-9a-f]{12}$` (the shape
SPEC §5.7 already mandates). Anything else raises `UnknownSessionError` before
touching the filesystem. The character-dropping sanitization is removed.
`engine.start`'s optional `session_id` override remains but callers (tests)
must supply conforming ids.

### 3.4 Mount: serialize `tree_answer` in-process

Tools become `async def` (FastMCP-native). `DecisionTrees` holds one
`anyio.Lock`; `tree_answer`'s load→submit→save runs under it. (Async-first here
also prepares Phase 2's elicitation, avoiding a threading→anyio churn.)
SPEC §5.7 note updated: in-process serialization guaranteed; cross-process
locking still explicitly not.

### 3.5 Cosmetics

- README test count corrected (58, and re-checked after this work).
- `engine._present()` (identity no-op) deleted; use `state.facts.get(name)`.
- `cli.render_mermaid` escapes `"` in node/edge labels as `#quot;`.

## 4. Phase 2 — spec 0.2 features

### 4.1 Trust model & determinism boundary (docs only, load-bearing)

New SPEC section (early, normative-adjacent) stating plainly:

- Engine traversal is deterministic **given reported inputs**. `action` results
  are agent-reported and unverified; the server cannot observe the agent's real
  tool calls.
- The trace is an honest record of *what was reported through which channel*,
  not proof of what happened.
- Elicitation (§4.2), when the client supports it, moves `ask` answers to a
  channel the model cannot fabricate; the trace `source` field records this.
- Client conformance (following the envelope at all) is cooperative; nothing
  server-side can force an agent to open a tree.

README gets a condensed version of the same paragraph.

### 4.2 `ask` reaches the human: MCP elicitation

Server behavior (all tree versions; not a tree-format feature):

- `tree_start` and `tree_answer` gain a FastMCP `Context` parameter and become
  the elicitation loop: whenever the computed envelope would be
  `awaiting_answer` (an `ask` node) and elicitation is enabled, the server
  calls `ctx.elicit(prompt, response_type=[option ids])` (enum ask) or
  `response_type=str` (free-text ask).
- **Accepted** → submit the answer into the engine with channel
  `source="elicitation"`, persist, and continue the loop (the next node may be
  another `ask`).
- **Declined / cancelled / client lacks the capability (exception)** → return
  the envelope exactly as today; the agent relays, answers arrive via
  `tree_answer` as before.
- The elicited submit re-loads state under the lock and submits against the
  step the elicitation was issued for; a concurrent advance surfaces as the
  normal `step_mismatch` in-envelope error (never a double-advance).
- An in-envelope error from an elicited answer (e.g. `fact_too_large`) ends the
  loop and returns that envelope.
- Opt-out: `DecisionTrees(mcp, trees_dir, elicit=False)`; the CLI gains
  `--no-elicit`.

**Trace change:** `TraceEntry` gains `source: str | None = None` —
`"elicitation"` (human answered via the client's elicitation UI),
`"tree_answer"` (submitted by the agent through the tool), or `null`
(auto-advanced `condition`/`terminal`). Old session files load fine (field
defaults). SPEC §5.5 documents it; `tree_trace` output includes it via
`asdict`.

Integration tests use FastMCP's in-process client with an
`elicitation_handler` (accept, decline, and unsupported-client paths).

### 4.3 Data flow: `{{ path }}` interpolation (0.2 documents only)

- Where: `action.args` (recursively through nested dicts/lists), `ask.prompt`,
  `judgment.prompt`, `terminal.summary`.
- Placeholder grammar: `{{ <fact path> }}` where fact path is the same dotted
  form `condition.on` uses. Regex:
  `\{\{\s*[A-Za-z_]\w*(?:\.\w+)*\s*\}\}`.
- **Whole-string placeholder** (`args: { service: "{{ service }}" }`) → the
  fact's value with its JSON type intact (numbers stay numbers, objects stay
  objects).
- **Embedded placeholder** (`"Deploy {{ service }} now?"`) → string
  substitution: the value itself for strings, compact `json.dumps` otherwise.
- **Missing fact** → the placeholder is left verbatim (visible and debuggable;
  never silent nulls — consistent with the fact-cap philosophy).
- Resolution happens at envelope-build time in the engine (deterministic: facts
  cannot change while a node is waiting). The pinned tree stores the raw
  template; the trace stores reported results, unchanged.
- **Gating:** documents declaring `"0.1"` get verbatim behavior (placeholders
  are just strings to them). Only `"0.2"` documents interpolate.
- **Load-time lint (0.2 only):** every placeholder's root segment must match a
  `capture` name declared somewhere in the tree (`ask.capture`,
  `action.result.capture`, `judgment.capture`); otherwise validation fails with
  `placeholder '{{x.y}}' references unknown capture 'x'`.

### 4.4 Predicate composition (0.2 documents only)

`when:` gains three recursive operators alongside the existing leaf ops:

```yaml
when: { all: [ { gte: 1 }, { lte: 2 } ] }   # and
when: { any: [ { eq: 200 }, { eq: 204 } ] } # or
when: { not: { eq: 200 } }                   # negation
```

- `all`/`any` take non-empty lists of predicates; `not` takes a single
  predicate; arbitrary nesting.
- All predicates in one `when` evaluate against the same `on` fact (unchanged).
- Leaf semantics unchanged (missing fact → `false` for everything but
  `exists`); composition is purely logical, so e.g. `not: {eq: 1}` on a missing
  fact is `true` — SPEC documents this consequence explicitly.
- In a `"0.1"` document, `all`/`any`/`not` fail parsing with a
  "requires mcptree 0.2" error.

### 4.5 Judgment capture (0.2 documents only)

`judgment` gains optional `capture: <fact name>`; on an accepted answer the
chosen option id is written to facts, so downstream `condition` nodes can
branch on a classification. In a `"0.1"` document the field fails parsing with
a "requires mcptree 0.2" error.

### 4.6 Versioning mechanics

- `models.SUPPORTED_VERSIONS = frozenset({"0.1", "0.2"})`;
  `Tree.spec_version` keeps the declared value; parse/validate/engine gate on
  it as above.
- SPEC.md becomes v0.2 in place (one living document; §6 explains that 0.1
  documents remain loadable and exactly what 0.2 adds).
- Python package version → `0.2.0`.

### 4.7 The 0.2 showcase tree: `trees/deploy.yaml`

A production deploy gate exercising every 0.2 feature (free-text ask capture →
interpolated action args and prompts → composite predicate → judgment capture →
condition on the captured classification → interpolated terminal summaries):

```yaml
mcptree: "0.2"
id: deploy-gate
title: Production deploy gate
entry: which_service

nodes:
  which_service:
    type: ask
    prompt: Which service is being deployed?
    capture: service
    next: check_ci

  check_ci:
    type: action
    tool: ci_status
    args: { service: "{{ service }}" }
    result: { capture: ci }
    next: gate_on_failures

  gate_on_failures:
    type: condition
    on: ci.recent_failures
    branches:
      - when: { all: [ { gte: 1 }, { lte: 2 } ] }
        then: assess_risk
      - when: { gt: 2 }
        then: block
    default: approve

  assess_risk:
    type: judgment
    prompt: "CI shows {{ ci.recent_failures }} recent failure(s) for {{ service }}. Are they related to this change?"
    evidence: [ci]
    options:
      - { id: related,   then: route_risk }
      - { id: unrelated, then: route_risk }
    capture: risk
    require_rationale: true

  route_risk:
    type: condition
    on: risk
    branches:
      - when: { eq: unrelated }
        then: approve
    default: block

  approve:
    type: terminal
    outcome: approved
    summary: "Deploy {{ service }}: approved."

  block:
    type: terminal
    outcome: blocked
    summary: "Deploy {{ service }}: blocked; resolve CI failures first."
```

Gets its own golden-trace test (asserting interpolated `expects.args`,
interpolated prompts/summaries, trace `source` values, and the
capture→condition route).

## 5. Testing & evidence

- TDD per feature (failing test first). Every defect in §3 gets a regression
  test reproducing the review's probe.
- Elicitation: in-process FastMCP client with `elicitation_handler` covering
  accept (enum + free text + chained asks), decline-falls-back, and
  unsupported-client-falls-back.
- Full suite + `mypy --strict` + `ruff check` green before any "done" claim.
- `capture` CLI shots of `mcptree validate trees/` and
  `mcptree viz trees/deploy.yaml` appended to `docs/test-evidence.md`.

## 6. Out of scope (recorded for later)

Sub-tree composition (`subtree` node type), PyPI publishing, session
listing/GC/TTL, session ownership/auth on shared servers, elicitation schemas
beyond enum/str, arg templating functions (only bare path substitution ships).
